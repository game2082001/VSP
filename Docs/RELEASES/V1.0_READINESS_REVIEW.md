## 2. Still Mandatory Before V1.0 GA

Exactly two capabilities, both from-scratch (verified directly against the repository — no `User`/`Role` type, no auth/login code, no backup/restore mechanism, no `User`-related SQLite table anywhere in the codebase):

### 2.1 User / Role
- Two fixed roles only: **Admin** and **Operator** — no custom roles, no granular permission matrix, no self-service registration, no SSO/external identity (all explicitly deferred, Enterprise).
- The precise Admin/Operator permission boundary is not yet defined — that's Epic-level scope for whichever Epic takes this on.
- Touches the security model (new auth, new schema) — will trigger `AI_OPERATING_SYSTEM.md` §8's Stop Conditions and needs its own Architecture Review before a Task Plan, the same rigor Settings/Theme got.

### 2.2 Database Backup / Restore
- Scope as currently defined: the SQLite file only (`%LocalAppData%\VSP\vsp.db`).
- Open question, not yet Product-Owner-confirmed either way: whether recordings/media, `recording-settings.json`, scheduling, or cloud backup are in scope — `V1.0_CUSTOMER_RELEASE_DEFINITION.md` §2.6 explicitly leaves these as open questions for that Epic's own definition, not pre-approved scope.
- `DatabaseService.CreateConnection()` is the only existing touchpoint today — no connection-open guard against a concurrent backup/restore exists yet, worth an explicit look when this Epic is scoped.

**These are the only two GA blockers.** Nothing else in the Definition's in-scope list (§2) is outstanding.

## 4. Technical Debt Acceptable for V1.0

Organized by how comfortable shipping GA with each item is, not by age.

### 4.1 Accept as-is — no customer-visible risk
- TD-029/TD-030 — `Environment.Exit(1)` as the shutdown mechanism (3 call sites). Correct and sufficient for a single-process desktop app; only becomes a real problem if/when a distributed Management/Recording Server split (Vision, v2.0+) is ever built. Flagged as the most architecturally significant *open* item in the codebase, but not a GA concern for v1.0's standalone deployment.
- TD-032 — dialog-building duplication in `App.xaml.cs`. Cosmetic, zero functional risk.
- Unnumbered, narratively-tracked items from the M2 Foundation Review's table (no formal TD-### assigned; carried in that review, not this document): Epic-010's `MediaError.Message` embedding raw native error text, `SetState`'s double lock-acquire (trivial), Epic-011's unchecked `av_interleaved_write_frame` return code, Epic-012's lack of frame-accurate position display. All low-severity, already accepted at their originating Epic's acceptance, no new risk found since.
- TD-033/034/035/037 (Epic-016, see §3.1) — Product-Owner-accepted at Epic-016's acceptance today as deferrable.
- Carried-forward Device Management-era items (TD-021 duplicate-camera check on Add, TD-026 background/auto refresh, TD-027 `TcpRtspTransport` overall-operation timeout, TD-028 additional RTSP transport robustness tests) — none touch a v1.0-required capability; all pre-date and are independent of Logging/Error-Handling/Settings.

### 4.2 Worth scheduling soon, not GA-blocking
- TD-031 — Playback's unlogged open-failure path. A customer-visible Playback failure today leaves no log trail, while the structurally identical Live View failure does. Recommend a narrow follow-up Epic before GA if time allows, otherwise as the first fast-follow after GA.
- `MediaController` SRP growth (no TD number assigned; tracked narratively since Epic-010, restated at every Foundation Review since). Not a functional risk today, but it has grown for three consecutive Epics without being paid down — worth a decision (accept as permanent shape, or schedule a decomposition) before it's touched by a sixth Epic.
- TD-022/TD-025 — no shared confirmation-dialog component. Each window (Camera Detail, Delete) rolls its own `MessageBox.Show`, functionally correct today but duplicated; worth consolidating if a third or fourth confirmation flow is ever added (Settings' Save flow, per Epic-016, deliberately used the same per-window pattern rather than waiting on this).

### 4.3 Stale documentation, not product debt
- `Docs/PROJECT_STATUS.md` is frozen at `v1.0.0-m1` / 88 tests / TD-001/TD-002 and has not been updated since — `Docs/03_PRODUCT_ROADMAP.md` and `Docs/CHANGELOG.md` are the current sources of truth. Recorded here so it isn't mistaken for an open product gap; fixing it is a documentation cleanup, not a v1.0 GA item.

**No item in this ledger blocks GA.** The only two blockers are the missing capabilities in §2, not any accumulated debt.

## 7. Release Readiness Process

A process description only — it does not add to, remove from, or reinterpret the GA requirements already recorded in §1–§5 above.

**Internal Validation → Pilot Customer Evaluation → General Availability (GA)**

### 7.1 Internal Validation
- Gate: every v1.0-required capability in §1.2 complete and individually accepted, including the two still open in §2.
- Full automated suite green.
- A Manual Validation pass against the actual built exe covering all five named capabilities together as one coherent product — not re-testing each Epic in isolation again, but exercising User/Role, Logging, Settings, Deployment, and Backup/Restore as a customer would encounter them in one session, the same rigor Epic-014/015/016 each applied individually.
- A clean-machine deployment verification, matching Epic-013's own precedent: xcopy install to an arbitrary path, no .NET runtime prerequisite reachable, a real functional smoke test against that installed copy.
- A security review of the full v1.0 surface, extending Epic-015's review to whatever credential/session-handling surface User/Role introduces.
- A documentation snapshot: `Docs/CHANGELOG.md`, `Docs/03_PRODUCT_ROADMAP.md`, and `V1.0_CUSTOMER_RELEASE_DEFINITION.md` all reflect the actual shipped state with no open discrepancy.
- Participants: internal only (Product Owner + AI Agent) — no external party yet.

### 7.2 Pilot Customer Evaluation
- Gate: Internal Validation passed.
- A limited, real-world deployment of the actual GA-candidate build (not a separate branch) to a small set of selected customers/sites.
- Change scope permitted during this phase: confirmed-defect fixes only, through the normal Task Plan → Approval → Implementation flow — no new features, no scope additions; a defect found here authorizes only the fix it requires, nothing broader.
- Feedback and defects are tracked back through the normal workflow, not a separate ad hoc channel.
- Duration and exit criteria (pilot length, number of sites, what counts as "no blocking issues remaining") are a Product Owner decision, not defined by this review.

### 7.3 General Availability (GA)
- Gate: Pilot Customer Evaluation passed, no unresolved blocking defect.
- `Directory.Build.props`'s `<Version>` becomes `1.0.0` — per the convention already recorded at Epic-013's acceptance: VSP becomes `1.0.0` only when every V1.0 GA requirement is complete and the Product Owner formally approves GA, not before.
- Final `CHANGELOG.md`/`03_PRODUCT_ROADMAP.md` entries mark v1.0 GA; `V1.0_CUSTOMER_RELEASE_DEFINITION.md`'s Status moves from "Approved" (scope) to "Shipped."
- Post-GA, every deferred item from §3 of this review — and anything new — proceeds as its own Epic against v1.1+, per the standing Roadmap convention.
