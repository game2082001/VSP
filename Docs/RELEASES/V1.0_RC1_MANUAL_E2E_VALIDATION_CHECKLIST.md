## One-time setup, before starting item B

- **Items B/C require a fresh, unmodified database** (default admin seeded with a forced password change). If `%LocalAppData%\VSP\vsp.db` already exists on this machine from earlier testing, its `admin` password has likely already been changed and `MustChangePassword` cleared — item C will not reproduce. Rename or move the existing `vsp.db` aside (do not delete — it may be needed to recheck later) so the app creates a fresh database on next launch.
- **Item L requires an Operator account.** No seeded Operator account and no account-creation UI exist in v1.0 — confirmed against source: `DefaultAdminSeeder` seeds exactly one Admin row and no other, and no `CreateUser`/user-management UI exists anywhere in `VSP.UI`. This is a documented Product Owner decision (`DefaultAdminSeeder.cs` comment, citing Epic-018 §8.2/§8.3), not an oversight, and is disclosed as a known limitation (see `V1.0_RC1_ACCEPTANCE_REPORT.md` §6). There is genuinely no supported production-UI path to create an Operator account in v1.0, so a direct database edit is the only option. To minimize risk and avoid needing to hand-compute a password hash, **clone the current `admin` row's password hash** into a new row rather than inventing new credentials: after item C is complete, close VSP, open `%LocalAppData%\VSP\vsp.db` in any SQLite tool, and run:
  ```sql
  INSERT INTO User (Id, Username, PasswordHash, PasswordSalt, PasswordIterations, Role, MustChangePassword, CreateTime, LastModifyTime)
  SELECT lower(hex(randomblob(16))), 'operator', PasswordHash, PasswordSalt, PasswordIterations, 1, 0, datetime('now'), datetime('now')
  FROM User WHERE Username = 'admin';
  ```
  This creates a new `operator` account that logs in with the **exact same password** as the current `admin` account (the one set in item C) — Role `1` = Operator per `VSP.Domain.Enums.Role`. No new hash to compute, no risk of a malformed hash locking the account out. Do not modify the existing `admin` row.

### Item E notes (resolved)

- **Batch Edit / single-selection disabled — CLOSED, working as designed.** Button's `CanExecute` (`SelectedItemCount >= 2`) is an explicit, spec'd requirement (`Docs\SPECS\Task-213_BATCH_EDIT.md`), covered by `CameraListViewModelBatchSelectionTests.cs`. Not a defect; no code change made. Retested and accepted with 2 cameras selected.
- **Defect 1 — RtspPort not honored at runtime — FIXED.** `RtspPort` was persisted but never consulted by `RtspCameraDriver.TestConnection`/`LiveViewViewModel` (hardcoded `554` fallback / raw `RtspUrl` passthrough). Fixed via `RtspEndpointResolver` + session-edit-intent-aware save normalization in `CameraDetailViewModel`. Verified with regression tests and manual retest.
- **Defect 2 — Camera Port (and other driver-setting fields) not editable in Camera Detail UI — FIXED.** `CameraDetailWindow.xaml`'s shared `DetailValueStyle`/`EditableTextBoxStyle` bound `IsEditMode` without a `RelativeSource`, so inside the driver-settings `ItemsControl` template (`DataContext` = `DriverSettingEditorViewModel`, no `IsEditMode` property) the trigger never fired — every driver-setting field (Port, Username, RtspUrl) stayed permanently read-only in both Add and Edit Camera, for every connection type. Fixed by adding `RelativeSource={RelativeSource AncestorType=Window}` to the two triggers. XAML-only change; verified manually for ONVIF HttpPort and RTSP RtspPort.
- Both fixes were reported verified in an initial Item E retest, but that Pass was **withdrawn** — a more rigorous manual retest against a real camera (192.168.0.89:1025) found the Camera Detail Port-editability fix did not actually work: `RelativeSource={RelativeSource AncestorType=Window}` binds to the Window *element itself* (which has no `IsEditMode` property), not its `DataContext` — so the trigger still never fired for driver-setting fields, and this incorrect fix additionally broke the previously-working Name field (and by the same mechanism, Model/IP Address/Location) by redirecting their working `{Binding IsEditMode}` away from `DataContext`.
- **Corrected fix** (`{Binding DataContext.IsEditMode, RelativeSource={RelativeSource AncestorType=Window}}`) implemented, approved, and **confirmed Pass by Product Owner manual retest** against the real camera (192.168.0.89, port 1025): saved Camera Port persisted correctly after reopen. Item E closed as Pass.

### Item F notes

- **Defect 3 — ONVIF Live View required a manually-configured RTSP URL — FIXED, VERIFIED.** Item F's manual retest against the real ONVIF camera (192.168.0.89:1025) surfaced a new defect: `LiveViewViewModel.LoadCamera` unconditionally required `camera.RtspUrl` to be set, regardless of `ConnectionType`, so an ONVIF-configured camera (which has no `RtspUrl` field in Camera Detail) always failed with "has no stream URL configured." Root-cause analysis found no ONVIF Media-service integration existed anywhere in the codebase — `OnvifCameraDriver` implemented only Device Management (`TestConnection`/`GetDeviceInformation`, Epic-007 scope); `StartLive`/`StopLive` were stubs. Epic-007's own spec explicitly deferred this ("Live View territory — separate, larger, likely-external-package Epic"), and that epic was never scheduled; against v1.0's combined release definition (Driver Framework RTSP+ONVIF, and Live View, both promised together) this is a genuine validation defect, not invented scope.
- **Fix**: added ONVIF Media-service stream URI resolution (`GetCapabilities` → discover Media `XAddr` → `GetProfiles` → deterministic first-profile selection → `GetStreamUri`), kept entirely separate from `ICameraDriver` (Option (b) — no public contract change) via a new `IOnvifStreamUriResolver`/`OnvifStreamUriResolver` in `VSP.Device.Drivers.ONVIF`. `LiveViewViewModel` now branches explicitly on `ConnectionType`: ONVIF resolves a stream URI dynamically and never falls back to a stored `RtspUrl` on failure; RTSP keeps its exact existing behavior unchanged. The resolved URI is never persisted (runtime-only, re-resolved every connect). Media (ver10) only for this fix; Media2 is a documented future addition point, not built here.
- Automated coverage: SOAP request/response construction and parsing (`GetCapabilities`/`GetProfiles`/`GetStreamUri`, Media `XAddr` extraction, profile token extraction, SOAP Fault, malformed XML), deterministic profile selection, full orchestration happy path and each failure category (Device Service unavailable, Media Service unavailable, authentication failure, no profiles, GetStreamUri failure, invalid stream URI) via loopback HTTP servers, and `LiveViewViewModel` regression tests (ONVIF resolves without needing `RtspUrl`, ONVIF failure does not start the player or fall back to a stored URL, no persistence of the resolved URI, RTSP cameras never invoke the ONVIF resolver). 818/818 tests passing at that point.
- **Defect 4 — Live View never authenticates with FFmpeg, for ONVIF or manually-configured RTSP — FIXED, VERIFIED.** Real-device retest against 192.168.0.89:1025 reached actual RTSP playback (proving ONVIF resolution itself works) but failed with `Server returned 401 Unauthorized`. Root-cause trace of the full credential path (`Camera.Username`/`Password` → `LiveViewViewModel` → resolved URI → `_controllerFactory` → `MediaController` → `RtspMediaSession` → FFmpeg `avformat_open_input`) found `Camera.Username`/`Password` were never attached to the playback URL anywhere, for *either* connection type — confirmed this is a pre-existing, shared gap, not ONVIF-specific: `RtspCameraDriver.TestConnection` has its own separate hand-rolled RTSP auth client used only for the Test Connection button; it shares no code with `RtspMediaSession`. FFmpeg's RTSP demuxer's only credential channel is the URL's userinfo (`rtsp://user:pass@host`) — confirmed by inspecting `MediaController`/`RtspMediaSession`, which have no credential parameter anywhere.
- **Fix**: new `RtspCredentialUriBuilder` (`VSP.Domain`) attaches percent-encoded `Camera.Username`/`Password` to the runtime playback URI only — never persisted, never written to `Camera.RtspUrl`. Used by both `LiveViewViewModel` paths via one shared call site (`StartAuthenticatedController`), so ONVIF and RTSP have identical authentication behavior. Precedence when a manually-typed RTSP URL already carries userinfo: an explicitly configured `Camera.Username` replaces it entirely (never concatenates); if `Camera.Username` is blank, existing URL userinfo is preserved unchanged for backward compatibility. `VSP.Player`/`ICameraDriver`/Repository/Schema untouched.
- Regression coverage added: exact-final-string assertions (not just `Uri.TryCreate` success) for reserved characters `@ : / % space # ?` in both username and password, verified via round-trip decode back to the original raw value; ONVIF+credentials, RTSP+credentials, both without credentials (unchanged from before); existing-userinfo-URL precedence and no-duplication; username-present-with-blank-password; credentials never appear in `StatusMessage`; authenticated URI never persisted to `Camera.RtspUrl`. 846/846 tests passing.

### Stop/Restart control-state fix (Item F — verified)

Found and fixed as part of closing out Item F: the Live View control bar had no way to restart Live View once stopped or errored — `StopCommand` was gated only on `HasCamera` (so it stayed clickable in states where there was nothing to stop) and there was no Play/Start Live command at all, so a Stop or an Error left the camera permanently unplayable without navigating away and back.

- **Fix**: added `LiveViewViewModel.PlayCommand` (`CanExecute` only when `State` is `Disconnected` or `Error`) that restarts Live View for the currently-loaded camera by re-invoking the existing `LoadCamera(Camera)` path — the same call `LoadCamera` already makes for the very first connect, so ONVIF stream URI resolution and RTSP/ONVIF credential attachment are redone from scratch on every restart, and the previous controller is detached/disposed (`LoadCamera`'s leading `DetachController()` call) before a new one is created, so Stop→Play and Error→Play can never produce a duplicate controller/session. `StopCommand`'s `CanExecute` was corrected to `State is Connected or Paused` (previously just `HasCamera`). Resume stays untouched and exclusive to `Paused` — Play never substitutes for it. Added a "Play" button to `LiveView.xaml`.
- Final `CanExecute` matrix — Connected/Playing: Pause Enabled, Resume Disabled, Stop Enabled, Play Disabled. Paused: Pause Disabled, Resume Enabled, Stop Enabled, Play Disabled. Disconnected/Stopped and Error: Pause/Resume/Stop Disabled, Play Enabled. Connecting/Reconnecting and Idle: everything Disabled.
- Automated coverage: `PlayCommand_OnlyExecutableWhenStoppedOrError`, `StopCommand_OnlyExecutableWhenPlayingOrPaused`, `PlayCommand_AfterStop_ReconnectsToSameCameraWithoutDuplicateController`, `PlayCommand_AfterError_ReconnectsToSameCameraWithoutDuplicateController` (`LiveViewViewModelTests.cs`). 897/898 tests passing (the one failure is the pre-existing, unrelated `RtspMediaSessionIntegrationTests` timing flake, confirmed passing in isolation).
- **Real-device retest (Product Owner, 2026-08-13)**, same artifact as above: **PASS.** Stop→Play confirmed working, repeated Stop→Play multiple times confirmed working (live video returns after each restart), no crash/freeze/duplicate-session symptom observed.
- Production code changed: `VSP.UI/ViewModels/LiveViewViewModel.cs`, `VSP.UI/Views/LiveView.xaml`. Test code: `VSP.Tests/Player/LiveViewViewModelTests.cs`. ONVIF resolver, RTSP authentication, Decoder, Renderer, `MediaController`, Recording, Playback, Repository, SQLite schema, Camera persistence, and Driver Framework were explicitly out of scope for this fix and were not touched.

### CurrentFrameSource / Frame Rendering Binding Fix (tracked independently — see RC1-R03)

This fix is **not part of Defect 3 or Defect 4 above**, and was tracked independently of Item F's pass/fail verdict (at the time still FAIL/BLOCKED) per explicit Product Owner instruction (Task-AI00B). It was found in the same `LiveViewViewModel.cs` working-tree diff while investigating Item F, but addresses a different, unrelated root cause, and — unlike Defect 3/4 — was never previously described anywhere in this checklist. Both this fix and Item F itself are now real-device validated and Pass (2026-08-13).

- **Problem**: even when a Live View connection reached Connected and frames were decoding and rendering successfully underneath the UI, the on-screen image could stay frozen at whatever it showed at the moment of connection (typically blank).
- **Root cause**: `IFrameRenderer.CurrentFrameSource` (pre-existing, unmodified) is updated in place by the renderer on every frame — same object identity, no `PropertyChanged` raised on its own. `WpfFrameRenderer`'s pre-existing `FrameRendered` event exists for exactly this purpose, but `LiveViewViewModel` never subscribed to it.
- **Fix**: `LiveViewViewModel.HandleFrameRendered` now subscribes to `controller.Renderer.FrameRendered` when a controller starts and unsubscribes when it is detached, raising `PropertyChanged(nameof(CurrentFrameSource))` on each frame.
- **Automated coverage**: three regression tests in `LiveViewViewModelTests.cs` — `PropertyChanged` fires on `FrameRendered`; the subscription is actually removed on detach; a stale, already-detached controller's late `FrameRendered` cannot update the current view model.
- **Validation status**: **Implementation Complete, Test Complete, real-device validated.** Covered by the Product Owner's 2026-08-13 Item F real-device retest (see above) — Live View displayed real, moving video (not a frozen first frame) across initial connect and every Stop→Play restart, which is only possible if `CurrentFrameSource` is being re-pulled on every frame as this fix requires. **Product Owner Accepted.** Full traceability in `Docs/SPECS/RC1-R03_LIVEVIEW_CURRENTFRAMESOURCE_BINDING.md`.
