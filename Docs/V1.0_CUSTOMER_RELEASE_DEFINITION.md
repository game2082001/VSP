## 1. Purpose

This document defines what VSP v1.0 actually ships to a customer: which capabilities are in scope for General Availability, and which remain explicitly Future. It is narrower than `PRODUCT_CAPABILITY_MATRIX.md`, which inventories the whole platform vision — this document is the committed subset for v1.0.

This is a Product Decision document. It authorizes no implementation by itself. Each item below still requires its own Spec/Task Plan and Epic-level approval before Coding begins, per `Docs/AI_DEVELOPMENT_WORKFLOW.md` and `AI/OperatingSystem/AI_OPERATING_SYSTEM.md`.

## 2. In Scope — v1.0

### 2.1 Already Implemented (prior Epics, unaffected by this approval)

Per `Docs/03_PRODUCT_ROADMAP.md` Versions 1.0–1.5 and Epic-013: Camera Management, Driver Framework (RTSP + ONVIF only), Discovery, Live View, Recording (Continuous only), Playback (Play/Pause/Stop/Seek only), Dashboard (read-only aggregation), and XCopy deployment. Not reopened by this document.

### 2.2 User / Role

- Exactly two fixed roles: **Admin** and **Operator**.
- No custom/configurable roles, no granular per-capability permission matrix, no self-service registration, no SSO/external identity — all deferred (Enterprise, §3).
- The precise permission boundary between Admin and Operator is Epic-level scope, not defined by this document.
- Current repository state: **no** User/Role/auth implementation exists anywhere in the codebase (no `User`/`Role` types, no login/authentication code, no `User`-related table — only the single `Camera` table exists in SQLite). This is a from-scratch capability.

### 2.3 Logging

- Moved from Optional to **Required** for v1.0 GA.
- V1.0 scope: a simple text log (plain file), not a structured/database-backed log, not the Audit Log capability (Audit Log remains a distinct, deferred Enterprise/Version 4.0 item — this is operational/diagnostic logging, not a compliance trail).
- Current repository state: **zero** logging infrastructure exists today — no `ILogger`, no Serilog/NLog/log4net, and no ad hoc `Console.WriteLine`/`Debug.WriteLine` diagnostic output anywhere in the codebase (verified by repository-wide search). This is a from-scratch capability.

### 2.4 Settings

- Exactly four settings for v1.0: **Recording Path, Retention Days, Language, Theme.**
- Everything else under the broader "Configuration" capability (`PRODUCT_CAPABILITY_MATRIX.md` §5.1, Not Started) is deferred.
- Current repository state: `SettingsView`/`SettingsViewModel` already exist in `VSP.UI`, already wired into `MainWindowViewModel`'s navigation — but both are empty placeholders (identical shape to `DashboardViewModel` before Epic-009). Separately, `RecordingPathProvider` (`VSP.Player.Recording`) already reads a config-file-backed `RecordingRoot` from `recording-settings.json` under `%LocalAppData%\VSP`, documented in its own source as "the smallest seam... for this and future Epics" — i.e. already built with a Settings UI in mind. Retention Days, Language, and Theme have no existing implementation of any kind.

### 2.5 Deployment

- XCopy deployment (self-contained win-x64 publish, no .NET runtime prerequisite) is **officially accepted** as the v1.0 GA deployment method.
- Installer/wizard technology (MSI, MSIX, Inno Setup, etc.) is **deferred** past v1.0 — remains an unscheduled future decision, not a v1.0 gap.
- Already implemented and verified: Epic-013 (`Docs/CHANGELOG.md`, 2026-07-31) — self-contained publish profile, `vsp.db` under `%LocalAppData%\VSP`, xcopy-to-arbitrary-path verified, FFmpeg payload trimmed to win-x64 only.

### 2.6 Database Backup / Restore (New for v1.0)

- Scope: the SQLite database file only — `%LocalAppData%\VSP\vsp.db` (per Epic-13's `DatabaseService`).
- Not stated by the Product Owner and therefore **not assumed** in scope unless confirmed at Epic definition: recordings/media backup, `recording-settings.json` or other config-file backup, scheduling/automatic backup, cloud backup, incremental/differential backup. Treat these as open questions for Epic-014's scope boundary, not as approved scope.
- Current repository state: no backup/restore mechanism exists today. This is a from-scratch capability. `DatabaseService.CreateConnection()` is the only existing touchpoint (single hardcoded path, no connection-open guard against a concurrent backup/restore).

## 3. Future — Explicitly Out of Scope for v1.0

All of the following remain **Future**, per the Product Owner's standing instruction and consistent with the existing 2026-07-29 scope freeze already recorded in `Docs/03_PRODUCT_ROADMAP.md` ("no AI, no Cloud, no Cluster, no Mobile"), extended here to the full list the Product Owner just restated:

| Category (as stated) | Maps to (`PRODUCT_CAPABILITY_MATRIX.md`) | Status there |
|---|---|---|
| AI | §5.5 AI / Analytics (all rows) | Not Started |
| Cluster | Cluster / HA, §5.7 Enterprise | Not Started (ADR-002 v7) |
| Cloud | ADR-002 v8 (cloud-relayed viewing, cloud storage) | Not Started |
| Timeline | Timeline Playback beyond the shipped Play/Pause/Stop/Seek — calendar/scrub UI, Search, Bookmark, Export, Snapshot, §5.4 | Not Started |
| Analytics | Smart Search, Heatmap, People Counting and related, overlapping §5.5 | Not Started |
| Plugin | Plugin Runtime (§5.1) and every Integration-category plugin — Access Control, POS, E-map/GIS, Video Wall, Notification, External API (§5.6) | Not Started |
| Mobile | Mobile App, Tablet, TV Wall, §5.8 | Not Started |
| Enterprise (broader) | Multi-site, Cluster/HA, Audit Log, License Management, independently-deployable Management/Recording Server split, AI Analysis Server, Storage Server, §5.1 / §5.7 | Not Started / Partial (Management + Recording Server remain intentionally co-located in the single desktop app for v1.0's standalone deployment) |

The narrow Database Backup/Restore item in §2.6 is a deliberate, scoped carve-out from the broader "Enterprise" Backup/Restore row in the Capability Matrix (which describes backing up all platform state, Vision §14) — it does not pull the rest of that row into v1.0.
