# VSP Video Pipeline Performance Baseline

This document is the authoritative performance baseline for the VSP media pipeline (ADR-002/ADR-003). It is established by Epic-010 (Live View Foundation) and is intended as the comparison point for every future Video Epic (Recording, Playback, Motion/AI, Transcoding, etc.) — a future Epic that regresses meaningfully against these numbers should treat that as a finding requiring explanation, not silently accept it.

## Methodology

- **Decode time**: a real `RtspMediaSession` (pointed at a real 1920×1080@30fps, 150-frame MJPEG file generated by the bundled `ffmpeg.exe`) feeds real encoded packets to a real `FfmpegVideoDecoder.Decode()`. Timed with `Stopwatch` around the `Decode()` call only (excludes any test-harness queueing).
- **Render time**: a real `WpfFrameRenderer` (the same class the shipped app uses) receives synthetic but correctly-shaped 1920×1080 BGRA32 `DecodedFrame`s, on a real `Dispatcher` pumped via `Dispatcher.PushFrame` (the standard technique for exercising WPF's dispatcher queue outside an interactive window). Timed from `OnFrame()` call to the `FrameRendered` event.
- **Reconnect time**: a real, public `MediaController` (the exact class the shipped app uses) is pointed at a real, finite 60-frame MJPEG file. Reaching end-of-file causes a genuine `Faulted` transition inside `RtspMediaSession` (indistinguishable, from `MediaController`'s perspective, from a real network fault), triggering the real reconnect loop, which reopens the same file. Timed from the `Reconnecting` state transition to the next `Connected` transition, via `MediaController.StateChanged` (public API only — no internal/test-only access used).
- **CPU/Memory**: `Process.TotalProcessorTime`/`Process.WorkingSet64` sampled immediately before opening the session and immediately after the decode loop completes, isolating the harness process from the separate encoder process used to generate test content.

## Caveats — read before comparing future Epics against this baseline

- **Codec**: measured against MJPEG, not H.264. MJPEG was used because the bundled LGPL-only FFmpeg build has no GPL-licensed H.264 *encoder* available to generate test content (the H.264 *decoder* is present and would be used for a real camera — this baseline does not exercise it). Decode cost per frame will differ for H.264 (typically more decode work per frame than MJPEG, partially offset by H.264's much smaller frame sizes reducing memory-copy cost) — revisit this baseline against a real H.264 camera stream once available.
- **Source**: decode/throughput and reconnect were measured against a local file, not a live RTSP stream over a real network to a real camera. Real-world reconnect time will additionally include TCP handshake + RTSP DESCRIBE/SETUP/PLAY round-trip time (camera- and network-dependent, typically an additional 100 ms–2 s for compliant IP cameras) on top of the ~17 ms of reopen overhead measured here.
- **Rendering**: measured headlessly via a pumped dispatcher, not the actual interactive WPF window/compositor. Real on-screen compositing cost (layout, visual tree, GPU presentation) is not included — only the `WritePixels` call itself.
- **Hardware acceleration**: not used or measured. This is a pure CPU-decode baseline despite a capable GPU (RTX 4080 SUPER) being present in the test environment.
- **Single stream**: all numbers are for one active Live View session. No multi-camera concurrency data exists yet.

## Known accepted debt affecting future measurements

Per the Epic-010 Architecture Review (see CHANGELOG Version 1.14), no buffer pooling exists in the decode/packet path (`ArrayPool<byte>` was identified as future work, not implemented). Sustained multi-minute/hour operation was not measured in this baseline — only a short burst (150 frames / ~0.5–2 s of decode activity). A future soak-test baseline (GC pressure, thread count, sustained memory trend over minutes/hours) is recommended before or alongside the next Video Epic that runs Live View continuously for extended periods (e.g. Recording).
