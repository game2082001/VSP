# Task-502 Discovery Session Foundation

Version: 1.0
Status: Draft
Feature: Discovery
Milestone: Version 1.5

---

# 1. Purpose

Task-502 establishes the Discovery Session Foundation.

`DiscoverySession` represents one Discovery execution lifecycle.

It is:

- an execution lifecycle aggregate
- an in-memory lifecycle model
- a wrapper around session identity, lifecycle state, timing, and snapshot reference

It is not:

- History
- a Repository Entity
- Progress
- Retry
- Timeout
- UI state
- Discovery logic

Task-502 does not modify production code.

Task-502 does not add tests.

Task-502 does not define persistence.

---

# 2. Architecture Overview

Formal pipeline:

`Discovery Source`

-> `DiscoveryOrchestrator`

-> `DiscoveryOrchestrationResult`

-> `DiscoverySessionFactory`

-> `DiscoverySession`

-> `DiscoverySessionSnapshot`

-> `DiscoveryOrchestrationSummary`

The orchestrator remains session-agnostic.

The session factory is the only component that creates `DiscoverySession`.

The session stores lifecycle information and references a snapshot.

The snapshot stores summary, reasons, and statistics for a point in time.

# 4. DiscoverySession

`DiscoverySession` is a lifecycle aggregate.

It represents one Discovery execution lifecycle.

## Allowed Fields

`DiscoverySession` may only store:

- `SessionId`
- `CorrelationId`
- `Status`
- `StartTime`
- `EndTime`
- `Duration`
- snapshot reference

## Disallowed Fields

`DiscoverySession` must not store:

- Candidate
- Driver
- Camera
- Repository
- Service
- UI State
- Progress
- Retry
- Timeout
- protocol payload
- discovery service instance

## Responsibility

`DiscoverySession` is responsible for carrying session lifecycle metadata.

It is not responsible for:

- running Discovery
- invoking Orchestrator
- creating snapshots
- persisting history
- reporting progress
- retrying failed work
- applying timeouts

---

# 5. DiscoverySessionId

`DiscoverySessionId` should represent a stable session identity.

Recommended model:

- strongly typed value object
- internally backed by a string or `Guid`
- can be generated by the session factory

Rules:

- must not be empty
- must not be treated as `CorrelationId`
- must identify exactly one discovery execution lifecycle

`CorrelationId` may group related operations.

`DiscoverySessionId` identifies a single session.

---

# 6. DiscoverySessionStatus

`DiscoverySessionStatus` represents lifecycle state.

Allowed statuses:

- `Created`
- `Running`
- `Completed`
- `CompletedWithErrors`
- `Cancelled`
- `Failed`

## Created

Entered when a session is initialized before execution has started.

This state may be used by future session runners.

Task-502 does not require a runner.

## Running

Entered when discovery execution is in progress.

Task-502 may define this state even if first implementation creates sessions from completed orchestration results.

## Completed

Entered when orchestration completes without candidate-level errors.

Recommended mapping:

- `DiscoveryOrchestrationResult.Status == Completed`

## CompletedWithErrors

Entered when orchestration completes but has candidate-level issues.

Recommended mapping:

- `DiscoveryOrchestrationResult.Status == CompletedWithErrors`

## Cancelled

Entered when caller cancellation stops orchestration.

Recommended mapping:

- `DiscoveryOrchestrationResult.Status == Cancelled`

## Failed

Entered when orchestration fails at request-level or infrastructure-level.

Recommended mapping:

- `DiscoveryOrchestrationResult.Status == Failed`
- invalid or unmappable orchestration result

---

# 7. DiscoverySessionSnapshot

`DiscoverySessionSnapshot` represents a point-in-time view of discovery session state.

It should contain:

- `DiscoveryOrchestrationSummary`
- `SessionReason[]`
- statistics

It must not contain:

- Candidate Details
- Driver Objects
- Camera Objects
- Repository
- Service
- UI State
- Progress
- Retry state

## Immutability Rule

`DiscoverySessionSnapshot` is immutable.

Existing snapshots must not be modified.

When execution state changes, create a new snapshot.

This rule allows future history and time-series tracking without mutating previous state.

---

# 8. Summary Reuse

Task-502 directly reuses:

- `DiscoveryOrchestrationSummary`

Task-502 must not create:

- `DiscoverySessionSummary`

Rationale:

- avoids duplicate summary models
- prevents counter drift between orchestration and session
- keeps Task-502 small
- preserves current Task-501 summary semantics

Tradeoff:

- `DiscoverySessionSnapshot` depends on `DiscoveryOrchestrationSummary`

This coupling is acceptable because the snapshot is derived from orchestration output.

If future persistence requires a stable storage DTO, Version 2 may introduce a mapper and persistence DTO.

---

# 9. SessionReason

`SessionReason` stores structured session-level reasons.

Recommended fields:

- `Code`
- `Message`

Rules:

- reason code must not be empty
- message must not be empty
- reasons should be human-readable and stable enough for testing

`SessionReason` may be derived from:

- `DiscoveryOrchestrationReason`
- future session-level validation
- future session factory errors

It must not contain:

- candidate object
- repository object
- UI command

---

# 10. DiscoverySessionFactory

`DiscoverySessionFactory` is the only creator of `DiscoverySession`.

Input:

- `DiscoveryOrchestrationResult`
- optional `CorrelationId`
- optional start time
- optional end time
- optional session id

Output:

- `DiscoverySession`

Responsibilities:

- create `DiscoverySessionId` when needed
- map orchestration status to session status
- compute duration from start and end time
- create immutable `DiscoverySessionSnapshot`
- copy or map orchestration reasons into `SessionReason`
- attach snapshot reference to session

It must not:

- run Discovery
- call `DiscoveryOrchestrator`
- call Driver Selection
- call Camera Factory
- call Registration
- write Repository
- access SQLite
- manage History
- emit Progress
- retry work
- apply Timeout

# 11. Relationship Diagram

```text
Discovery Source
    |
    v
DiscoveryOrchestrator
    |
    v
DiscoveryOrchestrationResult
    |  Status
    |  Summary
    |  Reasons
    v
DiscoverySessionFactory
    |
    v
DiscoverySession
    |  SessionId
    |  CorrelationId
    |  Status
    |  StartTime / EndTime / Duration
    |  Snapshot Reference
    v
DiscoverySessionSnapshot
    |  Summary
    |  Reasons
    |  Statistics
    v
DiscoveryOrchestrationSummary
```

Dependency direction:

- `DiscoveryOrchestrator` produces `DiscoveryOrchestrationResult`
- `DiscoverySessionFactory` consumes `DiscoveryOrchestrationResult`
- `DiscoverySessionFactory` creates `DiscoverySession`
- `DiscoverySession` references `DiscoverySessionSnapshot`
- `DiscoverySessionSnapshot` reuses `DiscoveryOrchestrationSummary`

Forbidden direction:

- `DiscoveryOrchestrator` must not depend on `DiscoverySession`
- `DiscoverySession` must not call `DiscoveryOrchestrator`
- `DiscoverySessionSnapshot` must not reference candidate details

# 12. Architecture Rules

## Rule 1

`DiscoverySession` is a lifecycle aggregate.

It must not own domain entities.

It must not hold `Camera`, Driver, Repository, Candidate details, or service objects.

## Rule 2

`DiscoverySessionSnapshot` is immutable.

New execution state must create a new snapshot.

Existing snapshots must not be modified.

## Rule 3

`DiscoverySessionFactory` is the only creator of `DiscoverySession`.

`DiscoverySession` should not be constructed ad hoc by Orchestrator, UI, Repository, or tests except through approved factory/test builder patterns.

## Rule 4

`DiscoveryOrchestrator` must remain session-agnostic.

The orchestrator must not create, mutate, persist, or query `DiscoverySession`.

# 13. Future Extension

Version 2 may add the following without modifying `DiscoveryOrchestrator`.

## SessionRecorder

`SessionRecorder` may wrap orchestration execution.

It may:

- mark session created
- mark session running
- create session snapshots from orchestration results
- pass results to a future session repository

It must not move session responsibilities into Orchestrator.

## SessionRepository

`SessionRepository` may persist sessions and snapshots.

It should depend on session models or persistence DTOs.

It must not require `DiscoveryOrchestrator` changes.

## History

History can be represented as a collection of immutable snapshots.

History should be added through session repository or recorder.

History must not make `DiscoverySession` mutable.

## Progress

Progress may be added through a future progress event model.

Progress should produce separate events or snapshots.

Progress must not be embedded into `DiscoverySession` first version.

## Retry

Retry may be added through a future retry policy or runner.

Retry must not be encoded into `DiscoverySession`.

## Timeout

Timeout may be added through a future execution policy.

Timeout must not be introduced in Task-502.

# 15. Risks

## Session Becoming God Object

Risk:

- Session may absorb progress, retry, timeout, UI, and history responsibilities.

Mitigation:

- keep `DiscoverySession` limited to lifecycle metadata and snapshot reference.

## Summary Duplication

Risk:

- creating `DiscoverySessionSummary` would duplicate `DiscoveryOrchestrationSummary`.

Mitigation:

- reuse `DiscoveryOrchestrationSummary` in `DiscoverySessionSnapshot`.

## Mutable Snapshot

Risk:

- mutating snapshots would make future history unreliable.

Mitigation:

- snapshots are immutable; new state creates a new snapshot.

## Session Owning Domain Objects

Risk:

- storing candidates, cameras, drivers, or repository objects would couple session to domain workflow internals.

Mitigation:

- session stores identity, lifecycle, timing, and snapshot reference only.

## Orchestrator Depending On Session

Risk:

- Orchestrator could become session manager or history recorder.

Mitigation:

- session creation belongs to `DiscoverySessionFactory`.
- Orchestrator remains session-agnostic.
